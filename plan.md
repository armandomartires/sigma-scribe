## 1. What the app is
A distraction-free Markdown/plain-text notebook for an e-reader (“the page is the product”): editor with autosave and on-screen keyboard, Markdown preview with wiki links/backlinks/graph, files and folders, options (Day/Night, Literata/Atkinson, size/leading/margin, words-per-line), side drawer (Contents, To-dos, Scratch), find & replace, help. Details: design-brief.md.

## 2. Target device (read-only probe 2026-10-20)
| Field | Value |
|---|---|
| Model | Kobo Forma (code 377, serial prefix N782, *frost*, Mark 7 / i.MX6 SLL, 512 MB) |
| Firmware | 4.38.23697 — **stay on 4.x** (NickelMenu does not support 5.x) |
| Panel | 8" 1440×1920 Carta 300 ppi, greyscale, rotation sensor |
| Input | capacitive touch, 2 page-turn buttons, power button; **no Bluetooth**; USB-OTG keyboard needs a powered hub / Y-cable |
| Storage | `/mnt/onboard` (vfat, 6.7 GB free); existing mod: NickelDBus 0.2.0 only |

## 3. Platform decision (S0)
**Cobalt dropped** because:
1. Cobalt's installer refuses the Forma: `kobo setup --dry-run` → “unsupported Kobo hardware: model code N782 has no reviewed Cobalt profile” (hard check in `crates/kobo-cli/src/setup.rs`; porting needs maintainer review + attended evidence).
2. Even if supported, the Cobalt SDK cannot meet the brief: no free-form drawing, no font choice, no colour/inversion (Night), no pixel layout (drawer, gutter, words-per-line), no multi-line text field (only a monospace terminal grid), notes in a key/value store (≤256 keys, ≤256 KiB) instead of `.md` files on USB, no raw input for USB keyboards. (docs/s0-findings.md)

**Plan B:** our own Rust app draws into an 8-bit canvas and pushes dirty rectangles to the panel with **FBInk** (NiLuJe, GPL-3.0-or-later, linked statically; compatible with AGPL-3.0). Touch and buttons are read from **evdev**. **NickelMenu** (pgaskin, v0.6.0, firmware 4.x) adds a menu entry that runs our launcher; the launcher stops Nickel, runs the app and **reboots back to the stock reader** on exit (the KOReader approach, simplified).

## 4. Architecture
```
crates/core    sigma-core   pure Rust, no platform deps: buffer, caret, measured wrap, keyboard model,
                            note store (atomic .md writes), autosave, text utils   [kept from S1]
crates/render  sigma-render 8-bit greyscale canvas, design tokens (brief §2 → grey), Literata (+ SemiBold, Italic) + Atkinson
                            Hyperlegible (SIL OFL, embedded) via fontdue, editor screen layout/draw/hit-test
crates/device  sigma-device `Device` trait (size, present(canvas, rect, Refresh::{Fast,Partial,Full}),
                            next_event → Tap/PageTurn/Power/Key/Quit), evdev decoder + touch transform,
                            FBInk backend (arm only, C shim + libfbink.a), headless PNG backend
app            sigma-scribe App loop (generic over Device); bins: sigma-scribe (Kobo: FBInk; desktop: live
                            minifb window), sigma-emu (headless scripts → PNG)
packaging/kobo              .adds/sigma-scribe/{launch.sh,touch.conf}, .adds/nm/sigma-scribe
```
- Notes are plain files: `/mnt/onboard/sigma-scribe/notes/*.md` (visible over USB; export = plug in USB).
- Refresh policy: keystrokes/caret → `Fast` on the changed rectangle only; keyboard toggle/scroll → `Partial`; first paint, theme, orientation, sheets → `Full` (flashing GC16).
- Layout tokens are brief px ×(panel width/1264) = ×1.139 on the Forma (44 px targets → 50 px).

## 5. Toolchain

Scripts: `scripts/build-armv7.sh`, `scripts/package-kobo.sh`, `scripts/sim.sh`.

## 9. Risks & open questions
- Touch transform on the Forma unverified (default `swap,mirror_x`, configurable in `touch.conf`; checklist §4).
- Stopping Nickel and rebooting on exit is robust but slow (~30 s); a later sprint can restart Nickel instead (as KOReader does).
- Rotation (gyro) handling and FBInk rotation quirks on Mark 7 — S4.
- USB-OTG keyboard / mouse (S8, S8.1, built): host mode with a wired 60% keyboard is known to work on this Forma (most likely via KOReader, whose role switch ours matches); the K400 Plus receiver and touchpad are untested, including whether two-finger scroll arrives as wheel events. Falls back to "no USB". See `docs/usb-keyboard.md`.
- Waveform choice for typing (AUTO vs DU) — measure on device.
- Never update the Forma to firmware 5.x.
- v0.2.2 touch: the Forma's lift signal (tracking id / pressure) and jitter while resting are unverified; if holds fire late or drags are jumpy, tune `Config` (hold_ms, slop) or the evdev MOVE_EPS. Palm / second-finger contacts are ignored (slot 0 only).
- Deletes were permanent in v0.2 (armed confirm only). Since the trash change (Unreleased) they move to `.trash/<time>/` instead; nothing empties it yet.
- Open from the brief: graph map vs list; Syncthing export later. (Edit-in-preview: decided read-only for v0.3, §10.12.)
- v0.3 preview speed on the Forma (parse + layout on toggle, on the UI thread) is unmeasured; a 100 KB note lays out in well under 1 s on a desktop debug build.

**Why this order:** the bug fix first (users hit it today). UI scale next because every later feature adds UI and must be laid out at the 200 % default — doing it later would mean re-laying out everything twice. Orientation is small and independent and benefits from the new scale. Latin layouts build the input pipeline and candidate bar that handwriting and the CJK IMEs reuse. i18n comes before RTL because the RTL release needs the string catalog and the mirroring switch (and fa/ar UI strings). Handwriting (Latin) before RTL/CJK: it proves the input-panel + candidate framework with the smallest model and alphabet, and its risky spike can fail without blocking the script releases (it is independent of them, so it can also move after v1.6 if the spike says "fallback"). RTL before CJK: shaping/bidi changes the text engine that CJK wrapping also touches; doing the deeper text-engine change once, earlier, avoids reworking CJK line breaking. Chinese last: it reuses the v1.7 converter, fonts and candidate UI.

**Key feasibility findings:** CJK — offline engines exist with AGPL-compatible licences (Mozc BSD-3 + permissive dictionary, SKK-JISYO GPL-2+, libkkc GPL-3, librime BSD-3 with LGPL-3 Rime data, libpinyin GPL-3); the practical route is an own Rust converter on Mozc (JP) and Rime (ZH) data, because Mozc/librime are heavy C++ cross-builds for armv7; dictionaries 10–40 MB, RAM 30–60 MB, conversion in ms on the A9 if mmap'd; fonts as separate files (JP/SC subsets ~2.5–3.5 MB per weight each, full Noto CJK ~19 MB) — storage is fine, the embedded binary is not. Handwriting — Tesseract (image OCR) and Google ML Kit Digital Ink (proprietary mobile SDK) are not usable; MyScript is commercial; the realistic open path is an own small BiLSTM/CTC model (1–2 M params, 1–8 MB) on tract, ~0.3–0.8 s per word on the Forma, with the main risk in training-data licences (IAM-OnDB and most online-ink sets are research-only); Zinnia (BSD) covers CJK single characters; fallbacks: word-at-a-time → single-character boxes → $P letter gestures.

## 12. ACCEPTED 2026-10-22: v1.5 handwriting, language coverage, Korean and Hindi
> **Accepted 2026-10-22 (decision 49): all 13 open decisions in §12.9 accepted at the recommendations.** Built and tested with the emulator and CI only; device checks go to `docs/device-checklist-prerelease.md` (decision 48). Sizes and efforts below are estimates.

### 12.1 What "handwriting" can mean on the Forma
- **Input hardware:** the Forma has **no pen digitizer** (no Wacom/EMR layer): only the capacitive `cyttsp5_mt` touch panel. A finger or a **passive capacitive stylus** (rubber/mesh tip ~5–6 mm) gives the same contacts. The driver reports `ABS_MT_POSITION_X/Y`, `ABS_MT_PRESSURE` and `ABS_MT_TOUCH_MAJOR/MINOR` (0–255, contact *area*, not force) with tracking IDs (Cypress TrueTouch Gen5 driver); the report rate while moving is estimated at a few tens of Hz and goes on the pre-release device checklist. So: coarse, sparse, jittery points; no hover; no pressure.
- **Consequences:** strokes need resampling + smoothing (Catmull-Rom between reports, light low-pass); writing must be large (a writing bar ≥ 25 mm tall); fine cursive is unrealistic, **print-style letters and short words** are realistic.

### 12.2 Recognition options (offline, ARMv7 A9, AGPL-compatible)
| Option | Licence | Fit on the Forma | Verdict |
|---|---|---|---|
| **$P / $Q point-cloud** template matcher (published algorithms, own code) | ours (AGPL) | single characters / gestures, < 1 ms, KB of templates; user-trainable | **v1.5.1 baseline** (character boxes) |
| **Zinnia** online SVM recogniser | BSD; Tomoe models LGPL | per-character, ms latency; CJK models exist, Latin needs training | reference; reuse for CJK later |
| **Lipi Toolkit** | MIT | dated, isolated characters | not planned |
| **Own small LSTM/GRU-CTC** (Carbune et al. 2020 style), run with **tract** (MIT/Apache, pure Rust) | ours | 1–2 M params, ~0.3–0.8 s/word est. on the A9 | **v1.5.2 gated spike** |
| ML Kit Digital Ink, MyScript, Apple/Windows HWR | proprietary | — | not usable |
| Tesseract (offline OCR) | Apache-2.0 | images, ignores stroke order; poor on handwriting | not suitable |

**Training data is the hard limit:** IAM-OnDB ("non-commercial research purpose only", fki.tic.heia-fr.ch), BRUSH (non-commercial research, Brown), DeepWriting (CC BY-NC-SA), OnHW (CC BY-NC) are **not usable** for a model we distribute in an AGPL app. Licence-clean sources: synthetic ink from single-stroke fonts (Hershey-style) with augmentation, and the **user's own ink** (opt-in, local only; decision 31). CC BY 4.0 online sets exist only for other scripts (e.g. OUHD-L, Urdu). → Recommendation: no third-party ink datasets.

### 12.3 Proposed scope, UX and storage
- **v1.5.0 — Ink panel + ink in notes (no recognition).** "Write" toggle on the keyboard bar (Keys ⇄ Write) swaps the keyboard area for a **writing panel** (white, baseline, Space / Backspace / Enter / Done). Two uses: **Insert ink** (the panel's drawing becomes an ink block in the note) and the input panel for later recognition. Finger / Stylus width (1.2 / 0.6 mm), first-contact-wins, second finger ignored, contacts outside the panel never ink. Undo last stroke.
- **v1.5.1 — Character boxes.** A row of 6–8 boxes; each box is recognised on lift + 500 ms with $P templates (a–z, A–Z, 0–9, punctuation, FR/PT accents via a second stroke); a 3–5 candidate row; **enrolment** screen to add your own templates (stored locally, decision 31). Inserted at the caret through the v1.3 composer.
- **v1.5.2 — Word mode spike + gate.** Small LSTM-CTC trained on synthetic + enrolled ink, tract on armv7 (QEMU timing in CI), lexicon EN/FR/PT. **Go** only if character error ≤ ~15 % on held-out enrolled ink and ≤ 1 s per word on the A9 estimate; else stay with boxes.
- **v1.5.3 — Gestures** (scratch-out delete, caret tap, line join) on the $P engine.
- **Storage format:** each ink block is a small **SVG** (polyline paths, mm units, black only) at `<note dir>/.ink/<note stem>/<id>.svg`, referenced from Markdown as `![ink](.ink/<stem>/<id>.svg)` so any Markdown viewer shows it; raw strokes (x, y, t ms, contact major) beside it as `<id>.strokes.json` for re-recognition. Preview renders our own SVG subset with a small polyline renderer (no runtime resvg). Export/Files treat `.ink/` like attachments (moved/renamed with the note). Enrolment templates under `notes/.handwriting/` (opt-in, deletable from Settings).

### 12.4 Refresh strategy (fast DU ink)
- Ink is **pure black on pure white** (no grey AA in the live stroke) so every update is DU-exact. Each input frame draws the new segment(s) and sends **one DU region** = segment bbox + stroke width, merged across a frame, **never waited for** (decision S10.3-D2). Optional **A2** waveform (FBInk `WFM_A2`) as an experiment flag for the device pass (faster, 1-bit).
- On pen-up + 600 ms idle: one **GL16** pass over the panel bbox to clear DU residue; recognition runs on a worker thread; candidates update with a Partial refresh. Ink blocks in the note/preview are drawn anti-aliased (GL16/partial) since they are static.
- Emulator: replay recorded stroke files (`tests/ink/*.json`), e-ink DU residue model already exists; metric = app-side ms per ink frame (target p95 < 8 ms).

### 12.7 Korean (proposed v1.7, with Vietnamese)
- **Layout:** Dubeolsik (2-set, KS X 5002) on-screen board (Shift for ㅃㅉㄸㄲㅆ, ㅒㅖ) and USB mapping of the physical US keys to Dubeolsik when layout = Korean; Han/Eng toggle on right Alt or `KEY_HANGEUL` (122), plus an on-screen 한/A key.
- **Composition:** a pure state machine in `sigma-core` (initial → medial → final, compound vowels ㅘㅙㅚㅝㅞㅟㅢ, compound finals ㄳㄵㄶㄺ…, final consonant moves to the next syllable on a following vowel), output as precomposed syllables (U+AC00 + (L×21+V)×28+T), **no candidate window**; Backspace decomposes the syllable jamo by jamo; the composing syllable is drawn underlined at the caret.
- **Font:** Noto Sans KR (OFL) subset to KS X 1001's 2,350 syllables + compatibility jamo ≈ 1.5–2 MB per weight (one weight for UI + text; Literata has no Hangul), or Nanum Gothic (OFL) ≈ 2–4 MB; full 11,172 syllables ≈ 3–4 MB as an optional "full" pack.
- **Effort/risk:** 1.5–2 wk; low–medium (composition edge cases, mixing with Markdown markers, font size). No shaping needed.

### 12.8 Hindi / Devanagari (proposed v1.9, after the shaping work)
- **Layout:** **InScript** (Government of India standard; on Windows/Linux) for on-screen and USB; a phonetic (ITRANS-like) layout as a later option.
- **Shaping:** conjuncts (virama + consonant), pre-base matra ि reordering, reph (र् + consonant → superscript), nukta — needs a real shaping engine: **rustybuzz** (MIT, pure Rust HarfBuzz port), the **same engine as the Arabic/Farsi/Urdu wave**, so v1.8 builds the glyph-run layout (shaped runs, cluster maps for hit-testing, wrapping by clusters) and v1.9 reuses it.
- **Caret / editing:** caret, selection and Delete move by **extended grapheme clusters** (unicode-segmentation, MIT/Apache); Backspace removes the last code point of the cluster (the common Indic expectation) — decision below.
- **Font:** Noto Sans Devanagari (OFL) ≈ 0.2–0.4 MB per weight; optional pack.
- **Effort/risk:** 2–3 wk on top of v1.8's shaping core (3–4 wk inside v1.8); high (editor layout moves from per-char advances to shaped runs; one rewrite shared with RTL).
