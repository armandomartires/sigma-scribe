# S10.4 — v1.0.4: pointer regression fix

**Status:** ✅ DONE (passed on the Forma, confirmed 2026-10-27); built 2026-10-22 · **Depends on:** v1.0.3

## Diagnosis
1.0.3 device log (two sessions, 00:53–01:00 CEST): `perf pointer` move-to-submit p50 170 / p95 333–344 / max 489 ms over 295 DU updates (the 1.0.1 figure, GL16 submit+complete p50 606 / p95 1091 ms, measured the panel, not the CPU); typing p95 95.6 ms in the 22-key session (1.0.1: 186.7), but 248 ms in a 4-key session; ~130 GL16 cleanups in ~6 min, far more than 3 s idle can cause. Causes: (1) every pointer move redrew the whole screen (~170 ms CPU on the Forma), so move events queued up and keys waited behind them; (2) idle was measured against the queued events' read time, so a backlog of >3 s looked idle and the arrow hid and reappeared over and over (flicker, many cleanups that collided with the next DU on the panel); (3) 1.0.3 sent the Graph pill on the pointer class, so it went out as DU instead of GL16.

## Fix (S10.4-D1)
- Pointer-only frames (`App::render_pointer_only`): copy the old arrow's rectangle back from the last full frame (kept without the arrow), draw the new arrow, present old∪new (≥16×16) as DU. Used only when nothing but the pointer changed (`pointer_fast`); any other event or a tick with work forces a full frame.
- Idle hide uses `max(event time, last tick)`, so queued moves never count as idle.
- Graph select / deselect: `Refresh::PointerCleanup` (GL16, one merged region) again.
- Unchanged: DU while moving, GL16 cleanup on hide, no completion waits, perf lines.

## Device check needed
Record `perf pointer:` p50/p95 (expect a few ms), typing p95 with the pointer in use, and the number of `gl16-cleanup` lines (expect about one per real pause).
